# 共用真机测试流程

## 1. 开始前的最小输入

明确 case ID、目标 App 与版本、平台、业务步骤、每步预期、测试环境、测试账号来源、是否需要人工验证、设备数量。业务规则不明确时先问最少必要问题，不生成预期结果。

## 2. 快速接入：先发现，再复用

1. 读取当前工作区的 `mobile-test/devices.md`（字段规则见 [设备档案](device-memory.md)），优先挑选最近验证过的设备和连接方式。
2. 读取 [用例记忆规则](case-memory.md) 和工作区 `mobile-test/cases/` 下当前 case 的平台记录。若 App 构建、起始页和前置状态匹配，直接按记录路径执行。
3. 在当前电脑上重新发现设备、驱动、App 包和前台状态；用实际识别值覆盖档案里的历史值。当前连接为 `device`/可用，不代表 App 已可测。
4. 建立一个最小会话：启动目标 App、读取非敏感页面标识、释放会话。登录态已存在时保留；不要为“干净环境”直接卸载或清数据。
5. 用一条冒烟 case 验证网络、账号、定位符和断言，然后开始目标 case。把本次有效的设备路径、端口、入口页面及阻塞记录写回工作区 `mobile-test/devices.md`；把可重放路径写回工作区对应 case 文件。

换电脑时先复制当前工作区和 skill、重新安装平台依赖，再执行上述步骤；换手机时重新发现 UDID/序列号、系统版本、尺寸和授权状态。不要把绝对路径、设备号、坐标、WDA 地址写死在通用用例里。

## 3. 单条 case 的执行与判定

| 步骤 | 必做动作 |
| --- | --- |
| 前置 | 确认测试账号、设备、网络、App 版本与起始页面；为并发 case 准备独立账号/数据。 |
| 操作 | 优先用资源 ID、无障碍标识定位；无法定位时结合截图和坐标，并记录设备尺寸。一次只做一个可观察动作。 |
| 观察 | 显式等待业务结果，读取页面状态；必要时截图。不能只以“点击成功”判定通过。 |
| 收尾 | 记录通过/不通过/环境阻塞/未执行，释放会话，更新设备档案。需还原的测试数据按事先约定处理。 |

AI 可以从已确认的需求起草 case 和脚本，但业务断言由人审核。验证码、Cloudflare 等人工验证应暂停自动化、提示用户操作，恢复后重新观察页面；不得把未完成步骤当通过。

## 4. 发现问题时立即记录

发现异常先在**当前工作区**保存当时的截图、App/设备/系统版本、时间和最近操作步骤；再按 [报告模板](../assets/bug-report.md) 写出预期与实际。优先在同一环境复现一次，区分真实产品缺陷、环境故障、自动化定位失败和测试数据问题。无法复现也保留首次证据并标明复现次数。

截图、页面源码和日志可能含账号、余额、地址、验证码等信息。只采集必要范围；分享前脱敏。每次运行的截图写到工作区 `mobile-test/runs/<运行批次>/`，真实 bug 报告与证据写到 `mobile-test/bugs/<bug-id>/`；不要把运行结果混进 skill 文件夹。

## 5. 多设备运行

- 设备清单至少记录平台、设备 ID、型号、系统版本、节点、App 版本、占用状态和上次验证时间。
- 调度时为每台设备加独占占用记录；每个会话有自己的设备 ID、端口、账号和输出目录。失败或超时后释放会话并检查设备能否再次使用。
- 先在两台设备上并行运行无共享数据的冒烟 case，再扩大矩阵。Android 端口见 [Android](android.md)，iOS 端口与签名见 [iOS](ios.md)。
- 汇总报告按 case ID、设备、App 版本和运行批次关联，避免把不同设备的结果混在一起。

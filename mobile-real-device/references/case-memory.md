# 用例路径记忆：首次探索，之后回放

设备档案解决“连上哪台手机”，本文件解决“这个 case 怎样快速到达目标按钮”。每个 case、平台、App 构建分别维护一份记录，存于**当前打开工作区**的 `mobile-test/cases/<case-id>/case.md`；自动化脚本放同目录。格式见 [模板](../assets/case-memory.md)。记录不含账号、密码、GA 码或钱包私钥。

## 首次执行

1. 确认起始页和前置条件，计时。只探索本 case 需要的页面。
2. 每完成一步，记录**首选定位符**（资源 ID / 无障碍标识）、必要时的后备定位符、预期页面校验点，以及该步耗时。坐标只能作为注明设备尺寸的最后手段。
3. 完成业务断言后保存总耗时、探索耗时、App 构建、平台、设备和验证时间。没有实际跑通的路径标记“待验证”，不能写成可回放。
4. 连续跑第二次前，先把已验证路径写入工作区的 case 文件；不要只留在临时会话或对话记忆中。

## 第二次及以后

1. 先检查 App 构建、平台、入口页和登录/网络等前置状态；匹配才使用缓存路径。
2. 直接按已记录定位符操作并验证每步结果。**不要再遍历整页、反复截图找同一个按钮，或重新猜导航路径。**
3. 仅当某步定位或校验失败，才对该步采集页面证据、局部重新定位并更新记录；不得跳过失败步骤继续可能产生业务后果的操作。
4. 记录本次总耗时与定位耗时。若同环境第二次不比第一次快，标记“速度回退”，说明耗时来自定位、设备、网络还是人工验证，并优化对应步骤；不能把未达成的速度目标写成通过。

例如某条 case 首次需要 10 秒探索：首次跑通后必须记住从**实际入口页**到目标按钮的已验证路径及定位符。第二次从相同入口直接回放。没有实际跑通的路径不能猜测或标记“已验证”。

固定网络请求、Cloudflare、GA 验证和设备负载会影响总墙上时间，无法承诺每次总时长绝对更短；可承诺不重复探索已验证页面，并用耗时记录发现回退。

Flutter 页面使用 Appium XML 时，`page_source` 原文可能将 `content-desc` 中的换行转义成 `&#10;`。等待或匹配多行无障碍标识时，先解析 XML，再读取解码后的 `content-desc` 属性；不要对原始 XML 字符串查找带换行的标签。动态余额等文本只匹配稳定前缀，并在点击后校验目标页。
